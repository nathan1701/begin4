==================================================================================
GHIDRA CONNECTION
==================================================================================

A live Ghidra MCP connection (tools named mcp__ghidra__*) was used throughout. Confirm it's live at
the start of the session (e.g. `get_current_function` - a "no function at this address" reply means
it's connected and working, not broken).

**This session's biggest lesson, and a real time-sink if you don't know to watch for it:** when a
decompiled function call has suspiciously few or opaque arguments (an `extraout_ECX`-style register,
or a function that looks like it's "called with nothing"), the real argument is very likely arriving
on the x87 FPU stack rather than as a normal parameter - Ghidra's high-level pseudocode can silently
misattribute it to the wrong caller-side expression, including inventing a plausible-looking but
WRONG constant reference. This happened three times this session, most expensively when the
decompiled phaser-damage formula confidently claimed a `4.0` literal that turned out not to exist
anywhere in the function's real instructions (raw disassembly showed `0.5`). When you see this
pattern, use `disassemble_function`, not `decompile_function`, and read the `FLD`/`FST`/`FSTP`
sequence directly. Full writeup: COMBAT_DAMAGE_MAP.md §5.

The other standing lesson (from the class-data mapping session, still relevant): a heuristic
file-offset table can be systematically wrong by a constant amount and still "confirm" several
fields by coincidence. When a code-confirmed offset disagrees with a heuristic/file-offset-based
one, trust the code-confirmed one, and if static analysis can't settle which is real, a live memory
read can - see ENERGY_SYSTEM_MAP.md §3.9 and this session's own live check (COMBAT_DAMAGE_MAP.md
§0) for two examples of exactly how and when to reach for that tool.
