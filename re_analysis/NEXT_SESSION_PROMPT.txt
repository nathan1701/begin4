LIVE GAME ACCESS AND METHODOLOGY (carries forward, proved decisive again this session)
==================================================================================

The developer plays the actual game interactively and can fly into combat, take torpedo and phaser
hits, get boarded/board others, and generally produce real ground truth on request - this was once
again the single most effective tool available this session, directly overturning a static-analysis
hypothesis (deferred damage) that looked entirely plausible from the code shape alone, and turning up
a whole new confirmed mechanic (derelict ships) that no static analysis had even been looking for.
Keep using it early and often, and keep watching for the developer's own incidental gameplay remarks
("I think my sensors are damaged," "he is grey in my tactical display," "I have to say, this is a
very fun strategy") - several of the best findings this session came from taking those seriously and
checking them against the code, not from a pre-planned investigation plan.

- `read_live_classdata.py --watch-combat [duration_seconds]` is the new tool for damage/hit-timing
  questions - it polls a ship's hit-counters and Shield array once per ~0.15s under one sudo prompt
  and prints only changed fields, the same pattern that worked for the Tube array last session.
  Extend `_snapshot_combat()`/`watch_combat()` rather than writing a new watcher if a next session
  needs to watch more/different fields (e.g. the still-unidentified array from
  `TORPEDO_IMPACT_MAP.md` §2.4/§6 item 3, or fields relevant to boarding/derelict state).
- **Before trusting a new watch function's field offsets, do a cheap one-shot sanity check first**
  (a single read, printed and eyeballed for plausibility) before launching a multi-minute watch.
  This session caught two real bugs this way with minimal wasted time: a wrong container-layout
  guess (an `OSError` from a garbage pointer, caught on the first sanity read) and a wrong field
  choice (`ship+0x110` "hull" - already known from last session to be scratch space, caught by
  seeing it read `0` at rest before wasting a 5-minute watch window on it).
- **Multiple Wine processes can be running for one game session** - this session had two `Begin.exe`
  PIDs simultaneously after a relaunch. Confirmed which was live by reading `DAT_004941c4` (the
  known ship-pointer global) from each and using whichever returned non-null, rather than assuming
  the lowest/first-listed PID from `ps aux` is correct.
- **The ship pointer (`DAT_004941c4`) going stale after ship destruction is a real, recurring
  limitation** - confirmed twice now (once last session, once again this session) that a direct
  read of `ship+0x1c` (destroyed status byte) shortly after death still shows `0`, not `3`, with the
  hit-counters frozen at their last live value. The literal moment of destruction has never been
  captured. If a future session wants that moment specifically, a different approach is needed -
  possibly polling faster right as death is imminent, or finding a path to the ship object that
  doesn't go through this specific global pointer.
- The PID changes every time the game restarts - always confirm with `ps aux | grep -i begin.exe`
  (and disambiguate multiple PIDs as above) rather than assuming a PID from earlier in the session
  is still valid.
- Sudo prompts require an interactive terminal - use the terminal-panel tool rather than a sandboxed
  shell tool that can't supply a TTY for the password prompt. Long `--watch`/`--watch-combat`
  durations (5-10 minutes) are worth defaulting to, since they avoid needing to re-prompt for sudo
  mid-experiment - this session used 300s and 600s windows.
- This is confirmed to be a turn-based game - keep this in mind when reasoning about timing;
  wall-clock gaps between events reflect how fast the player is typing/submitting turns, not a fixed
  real-time clock.

==================================================================================
GHIDRA CONNECTION
==================================================================================

A live Ghidra MCP connection (tools named mcp__ghidra__*) was used again this session, including for
a genuinely new technique: **Ghidra's MCP tools have no raw memory/data-read primitive** (no way to
read a vtable's actual pointer values, only xrefs to its address). Worked around this session by
disassembling a constructor to find a vtable's address as a literal operand, then using
`energy_system_analysis.py`'s existing `read_constant_at_address()` against the binary file on disk
to dump the vtable's raw pointer entries. Reusable pattern for any future vtable-slot lookup - see
`TORPEDO_IMPACT_MAP.md` §7.

Confirm the connection's live at the start of the session (e.g. `get_current_function` - a "no
function at this address" reply means it's connected and working, not broken).

The FPU-hidden-argument decompiler trap from COMBAT_DAMAGE_MAP.md §5 is still the standing lesson
for any new disassembly work - watch for decompiled calls with suspiciously few/opaque arguments
right after floating-point operations, and fall back to `disassemble_function` over
`decompile_function` when it shows up. It did NOT come up this session (every function decompiled
cleanly), but as with last session's note about `FUN_0040bf70`'s trajectory math, several functions
this session (`FUN_00405b50`'s damage formula in particular) haven't been hand-verified against raw
disassembly - don't assume clean decompiler output is automatically correct just because nothing
looked obviously wrong at a glance.
