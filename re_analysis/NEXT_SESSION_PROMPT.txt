LIVE GAME ACCESS AND METHODOLOGY (carries forward, proved its worth again this session)
==================================================================================

The developer plays the actual game interactively and can load/aim/fire torpedoes, fly evasive
maneuvers, and generally produce real ground truth on request - this was used constantly and
successfully this session (not just as a last resort) and directly overturned two separate
mid-session hypotheses (an "auto-fire" theory and a "field_34 is a fire order" theory) that static
analysis alone had gotten wrong or left ambiguous. Keep using it early and often, especially for:

- The torpedo projectile's post-launch behavior (next session's main topic) - the developer can
  fire a torpedo and then either let it fly to impact or maneuver to dodge it, both of which are
  exactly the kind of dynamic behavior static disassembly struggles to infer from scratch.
- `read_live_classdata.py --watch [duration_seconds]` is the tool to reach for - it polls
  repeatedly under one sudo prompt and only prints changed fields, which is what made catching the
  single-instant `ready(+0x30)` flag possible this session (a single before/after snapshot missed
  it completely). Extend `_snapshot_tubes()`/`watch_tubes()` rather than writing a new watcher -
  they're already structured to add more addresses/fields to poll if the projectile object's own
  address becomes known (e.g. by reading a "most recent torpedo" pointer, or scanning a suspected
  in-flight-projectiles list once found).
- The PID changes every time the game restarts (was 117796, then 124275 after the player's ship was
  destroyed and the game was relaunched) - always confirm with `ps aux | grep -i begin.exe` rather
  than assuming a PID from a previous session or even earlier in the same session is still valid.
- Sudo prompts require an interactive terminal - use the terminal-panel tool (types the command into
  a real tab the user can type their password into) rather than a sandboxed shell tool that can't
  supply a TTY for the password prompt. Long `--watch` durations (multiple minutes) are worth
  defaulting to since they avoid needing to re-prompt for sudo mid-experiment.
- This is confirmed to be a turn-based game (state only advances on a processed command, including
  a "did nothing" blank Enter) - keep this in mind when reasoning about timing; wall-clock gaps
  between events reflect how fast the player is typing/submitting turns, not a fixed real-time
  clock. A rejected/typo'd command can still consume a turn even though it does nothing else.

NEXT SESSION: TORPEDO PROJECTILE POST-LAUNCH BEHAVIOR (suggested name, pick your own if focus shifts)
==================================================================================

TORPEDO_DAMAGE_MAP.md traced the fire chain down to the exact moment `FUN_0040bf70` allocates a new
~280-byte projectile object (`FUN_0043d97e(0x118)`) via `FUN_00405830`, seeds it with a
target/trajectory snapshot, and returns. Nothing about what happens to that object afterward - its
travel, its "arms after N cycles" timer (manual flavor text, already known), collision detection
against ships, or the actual damage-on-impact call - has been traced yet. This is a structurally
different kind of hunt than either weapon session so far: instead of one self-contained per-ship
fire function, expect to be looking for wherever the game keeps a list of "things in flight" and
updates them once per turn, independent of any specific ship's own per-turn handler.

Useful running starts:
- The projectile object's constructor is `FUN_00405830` (`TORPEDO_DAMAGE_MAP.md` §1.3/§4) - check
  its other callers (`get_function_xrefs`), and check what vtable (if any) the object gets
  constructed with, the same way `Ship::vftable+0x34` was found by reading the ship vtable directly
  in COMBAT_DAMAGE.
- The manual's own already-known strings ("The torpedo arms after %.0lf cycle%s then remains
  stable...", "travels at a velocity of...") are a ready-made source of xrefs to whatever code
  handles the arming/travel timer - `get_xrefs_to` on those two string addresses (already listed in
  ENERGY_SYSTEM_MAP.md's game-strings pass) hasn't been checked yet.
- Torpedo damage is still known to copy a charge value into the projectile at
  `torpedo+0xf0` (TORPEDO_DAMAGE_MAP.md §1.3/§4) - if a damage-application call is found, check
  whether it goes through the already-known `Ship::vftable+0x34` (`FUN_00404d90`,
  COMBAT_DAMAGE_MAP.md §4) the same way Bank's does, and whether it passes weaponType=1 (the
  shield-bypass type from COMBAT_DAMAGE_MAP.md §2.2 - still an open guess that this is torpedoes).
- Live testing angle worth trying early: fire a torpedo, then use `read_live_classdata.py --watch`
  (extended to poll whatever address turns out to hold the projectile, once found statically) to
  watch its own fields change turn-by-turn as it travels - the same technique that successfully
  caught the tube's `ready` flag this session should work just as well on the projectile's own
  arming/travel state, and the developer can deliberately dodge or hold course to produce both a
  hit and a miss on request.
