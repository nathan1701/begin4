CRITICAL CONTEXT - WHAT PATH B5 ESTABLISHED
==================================================================================

The "WES:RES 4:1" hypothesis is now fully closed, in both directions:
1. DRIVE and SHIELD both use the real 4.0 literal (0x00464ad8) for two separate, real
   game-balance rules (Path B4).
2. WEAPONS (Bank, confirmed Path B5 via FUN_004087b0) use NEITHER 4.0 NOR any reactor-relative
   ratio at all. Cost = flat reactor-rate deduction + a separate type-specific per-tick charge
   cap (maxCharge/chargeRate, epsilon-clamped at 0x00465440=0.001). If the reactor can't cover
   its own rate for a tick, Bank's accumulated charge resets to ZERO - a harsher failure mode
   than Drive/Shield.
3. FUN_0040b510 (flagged in Path B4 as charge-cycle-shaped, using both 4.0 and 0.5) turned out
   to be a COMPLETELY SEPARATE system: a ship-wide "power-to-weight ratio" (reactor output /
   class Dead Weight Tonnage, computed in FUN_004035b0) driving probabilistic malfunction/event
   rolls for 5 subsystem slots (+0xb50, Tractor +0xb88, +0xbb8, +0xbf0, Cloak +0xc20). It
   coincidentally reuses the same 4.0/0.5 literals as the real energy system but never touches
   the reactor pool (local_88 from FUN_00404250). Don't confuse the two systems again.

Two functions this session (FUN_00412bb0 "Bank::ChargeCommand" and FUN_00408b80
"Bank::MarkUnitsState") were NOT in Ghidra's function database at all, despite being real code
- one of them a direct CALL target. Both were hand-disassembled from raw bytes. If you hit
"no function found at or containing address" from Ghidra on a region you have independent
evidence contains real code (e.g. a raw-byte pointer search hit), don't assume it's unreachable
- dump the bytes and decode by hand, or ask the user to create the function in the Ghidra GUI
(right-click -> Disassemble, then Create Function) so future MCP calls can reach it normally.
